\begin{abstract}
%==============================================================================
We design, implement, and evaluate a hardware matrix transpose unit within a neural-network accelerator's global buffer (GBCore) subsystem. Starting from a naive element-by-element baseline, we develop an optimized diagonally-banked-BRAM transpose that achieves up to \textbf{1.26$\times$} speedup on $16\!\times\!16$ matrices in RTL simulation on AWS F2. We then extend the module to support fused $Q\!\cdot\!K^T$ computation, where the fused variant reads the transposed $K$ directly from on-chip BRAM instead of round-tripping through SRAM, achieving up to \textbf{3.18$\times$} measured
speedup on $16\!\times\!16$ matrices. The entire design is verified through SystemC simulation, Catapult HLS synthesis, Vivado XSIM RTL simulation, and FPGA tests on the AWS F2 FPGA development platform.
\end{abstract}

%==============================================================================
\section{Introduction and Motivation}
%==============================================================================

Transformer-based models require frequent matrix transpositions. Most notably, matrix transposition is a bottleneck for memory-bound models as it has 0 arithmetic intensity. Mobile
profiling across several Transformer models reports that 43\%--70\% of
execution time can be spent on implicit and explicit data layout
transformations~\cite{smartmem}. 

On custom accelerators, the transpose is typically handled by address remapping within the global buffer, but a naive element-by-element implementation becomes a bottleneck because every read--write pair serializes through the shared SRAM interface. FPGAs offer a structural advantage: custom streaming datapaths and banked on-chip memories (BRAM) make conflict-free access a design-time property~\cite{fpga_xpose}, providing a direct path to end-to-end speedups.

Our project builds on the NVDLA-derived accelerator from Lab~4 and pursues three progressively goals:

\begin{enumerate}[nosep]
  \item \textbf{Implement an efficient hardware transpose unit} that exploits diagonal BRAM banking to prevent bank conflict and to reduce SRAM access states per element.
  \item \textbf{Demonstrate speedup} over the naive element-by-element transpose baseline via RTL simulation and FPGA implementation.
  \item \textbf{Fuse transpose with matrix multiplication} ($Q\!\cdot\!K^T$) so that the transposed operand is consumed directly from local BRAM without being written back to SRAM. This should result in higher speedup than the speedup in the previous goal.
\end{enumerate}

\section{Problem Statement}
%==============================================================================

We target the transpose that appears in the Transformer attention blocks. A standard attention implementation loads blocks of $Q$ and $K$,
computes $S = QK^T$, then writes intermediate matrices back to
memory~\cite{flashattn}. For BERT-base~\cite{bert}, the hyperparameters are $L = 12$ layers, hidden size $H = 768$, and $A = 12$ self-attention heads, giving a per-head dimension of $H/A = 64$. This defines the tensor shapes our design targets.


\subsection{Why FPGA?}
GPUs handle transpose is bottlenecked by DRAM bandwidth when the transposed operand must be materialized before the subsequent GEMM. CPUs offer cache-blocking strategies, but they cannot pipeline the transpose directly
with the downstream kernel.
FPGAs provide three structural advantages that CPUs and GPUs can't match:
\begin{enumerate}[nosep]
  \item \textbf{Conflict-free banked memory at design time:}
        An FPGA designer chooses the number of BRAM banks and the banking
        function so that every column (or row) access pattern hits distinct
        banks, eliminating runtime bank conflicts.
  \item \textbf{Operator fusion across memory hierarchy boundaries:}
        Because the transpose and the matmul are separate HLS modules sharing
        on-chip BRAM through explicit streaming channels, the transposed $K$
        never needs to be written back to global SRAM before being consumed
        by the matmul.  On a GPU this would require a separate kernel launch
        and a global-memory round-trip.
  \item \textbf{Configurable streaming datapaths:}
        The II\,=\,3 pipeline allows fill and drain phases to overlap
        computation with memory access at fine granularity.
\end{enumerate}

\subsection{Task} Design and implement a streaming, bank-conflict-free transpose
unit within the \texttt{GBModule} subsystem of a custom FPGA accelerator such
that:
\begin{enumerate}[nosep]
  \item The number of SRAM access states per matrix element is reduced relative to the naive element-by-element baseline.
  \item The transposed $K$ operand can be fused into a subsequent
        $Q\!\cdot\!K^T$ matmul, eliminating redundant SRAM write-back and
        re-read traffic.
\end{enumerate}

\subsection{Constraints and assumptions}
\begin{enumerate}[nosep]
  \item The \texttt{GBCore} interface serializes all accesses to one 128-bit element per transaction, pipelined at II\,=\,3 cycles. This is the primary throughput limit.
  \item The local BRAM supports 32 banks $\times$ 32 entries $= 1024$ elements (128-bit each), constraining matrices to at most $32\!\times\!32$.
  \item Each 128-bit vector packs 16 \texttt{uint8} scalars. Correctness is verified on the lower 8~bits of each dot-product accumulation.
  \item All data resides in on-chip SRAM; there is no DRAM or HBM interface.
\end{enumerate}

\section{Background: Lab~4 Baseline Architecture}
%==============================================================================

Our project extends the Lab~4 accelerator, which is the system baseline. This
section describes its architecture in detail; the gap it has regarding
transpose is the motivation for our work.

\subsection{Top-Level Structure}

The accelerator accepts AXI4 traffic (128-bit data, 32-bit address) from the
host. An \texttt{AxiSplitter} decodes the top 8~bits of the address and routes each transaction to one of $1 + \texttt{kNumPE}$ subordinates:

\begin{itemize}[nosep]
  \item \textbf{GBPartition} at base address \texttt{0x33000000}: global
        buffer, data I/O, and near-memory processing.
  \item \textbf{PEPartition}~$i$ at \texttt{0x3(3+i)000000}: systolic MAC
        array for one compute tile.
\end{itemize}

Four \texttt{DataBus} modules manage inter-partition signaling:
\texttt{PEStart} fans a single start token from GB to all PEs;
\texttt{PEDone} aggregates per-PE done tokens into one all-done signal;
\texttt{GBSend} broadcasts 128-bit activation vectors from GB to every PE;
\texttt{GBRecv} arbitrates the result streams from all PEs back to GB. An
\texttt{Interrupt} module asserts the IRQ line for 10 cycles once GB signals
completion.

\subsection{GBPartition / GBModule}

The global buffer partition exposes a single AXI subordinate interface whose
24-bit local address is decoded by the \texttt{GBModule} routing thread into
four submodules:

\paragraph{GBCore (SRAM scratchpad).}
Implements a 128-bit scratchpad with 16~banks $\times$ 4096~entries each,
for a total capacity of $16 \times 4096 \times 16\,\text{B} = 1\,\text{MB}$.
Every memory ``element'' is a 128-bit word (16 $\times$ \texttt{uint8}
scalars). 

\paragraph{GBControl.}
Manages PE$\leftrightarrow$GB streaming data transfer. On a start trigger
(\texttt{0x0}/\texttt{0x1} via AXI), it reads the activation vectors 
and streams them to PEs through \texttt{data\_out}; after all PE signal is received, it collects the result vectors from \texttt{data\_in} and writes them back to SRAM.

\paragraph{NMP.}
Performs RMSNorm or Softmax in-place on an SRAM region. Reads vectors from
GBCore, accumulates statistics (sum-of-squares or max/exp), and then writes
normalized values back. 

There is no hardware transpose unit in the Lab~4 \texttt{GBModule}. Any matrix transposition (e.g., forming $K^T$ for self-attention) must be performed in software before the data is loaded into SRAM.

\subsection{PEPartition / PEModule}

Each \texttt{PEModule} contains a \texttt{PECore} and an \texttt{ActUnit}.
\texttt{PECore} holds two \texttt{ArbitratedScratchpadDP} memories for weights
and inputs, and a \texttt{Datapath} module that performs dot-product
accumulation (GEMM inner loop) across the weight and input banks. 

\subsection{Execution Flow (Lab~4)}

\begin{enumerate}[nosep]
  \item Host configures GBCore base addresses and GBControl/NMP parameters
        via AXI.
  \item Host loads input activations and model weights into GBCore SRAM and
        PE weight SRAMs via AXI.
  \item Host sends start token to GBControl; GBControl streams activations
        to PEs.
  \item PEs perform GEMM + activation; done tokens propagate through
        PEDone to GB.
  \item GBControl collects PE outputs into SRAM. NMP optionally applies
        RMSNorm/Softmax.
  \item GB asserts \texttt{gb\_done}; Interrupt module fires IRQ.
\end{enumerate}


\subsection{Memory system and data movement}

Configuration and matrix data reach the custom logic along a single logical path: host $\rightarrow$ PCIe $\rightarrow$ OCL AXI-Lite
(MMIO registers in \texttt{design\_top}) $\rightarrow$ a bridge that issues AXI4 $\rightarrow$ \texttt{AxiSplitter} $\rightarrow$ GBPartition or PEPartition. This is how the host loads activations and weights, programs base addresses, and reads results back.

After data resides in \texttt{GBCore}, the Lab~4 baseline moves vectors between SRAM and PEs via \texttt{GBControl} streaming channels. There is no DRAM or HBM attached inside our CL.

Although AXI4 allows bursts, \texttt{GBCore} presents a serialized client interface: one 128-bit element per accepted request, pipelined at II\,=\,3 clock cycles. 

Our extension adds a dedicated \textbf{1024-entry transpose BRAM} with
diagonal banking inside \texttt{GBModule}; for fusion, $K^T$ is kept in that BRAM and is reused across the matmul inner loop instead of eing re-read from SRAM.

\section{Workload Characterization}
\label{sec:workload}
%==============================================================================

\subsection{Computation and Data Movement}
For an $N\!\times\!D$ matrix with 128-bit (16-byte) elements:

\begin{itemize}[nosep]
  \item Data read: $N \cdot D \cdot 16\,\text{B}$
  \item Data write: $N \cdot D \cdot 16\,\text{B}$
  \item Total data movement: $32\,N\!D$ bytes
  \item Arithmetic intensity: $0$ FLOPs/byte
\end{itemize}

Transpose performance is entirely determined by memory access efficiency.

In $Q\!\cdot\!K^T$, row $Q[i][*]$ is reused $N$ times (once per output
column $j$), and column $K[j][*]$ is reused $M$ times (once per output
row $i$).  The fused version exploits this by loading $K$ into BRAM
once (fill phase) and reading each $K[j][k]$ entry $M$ times from the
single-cycle BRAM rather than from the II\,=\,3 SRAM.

\subsection{Dominant Bottleneck}

The GBCore SRAM interface is a \textbf{single-port, serialized channel}:
one 128-bit element per transaction, pipelined at II\,=\,3 cycles (one
new request accepted every 3 clock cycles).  This single port is shared
among all clients (GBControl, NMP, and Transpose) and is the sole path to
on-chip storage. Since transpose has zero arithmetic intensity, the
entire workload is bottlenecked by this port.

\subsection{GPU Theoretical Baseline}

We provide a \textbf{theoretical GPU roofline estimate} for the same
$16\!\times\!16$ transpose and $16\!\times\!16\!\times\!16$ matmul
benchmarks that are directly measured on our FPGA design.

Total data movement: $2 \times 16 \times 16 \times 16\,\text{B} =
8\,\text{KB}$.  On an NVIDIA A100 with HBM2e peak bandwidth of
2\,TB/s, the minimum memory-bound time is $8\,\text{KB} /
2\,\text{TB/s} \approx 4\,\text{ns}$.  However, the minimum CUDA kernel
launch latency is approximately 5--10\,$\mu$s~\,
over $1000\times$ larger than the memory-bound time.  For such small
matrices, the GPU is kernel-launch-overhead-bound, not
compute- or bandwidth-bound.

Our FPGA design avoids this entirely: the transpose is triggered by a
single AXI write already on the critical path and produces output
directly in SRAM, with zero kernel-launch overhead.


\subsection{Host/FPGA Partitioning}

The programming model is specified in Section~\ref{sec:methodology}.

\paragraph{What runs on the host?}
\begin{itemize}[nosep]
  \item AXI configuration writes: base addresses, matrix dimensions, opcode.
  \item Data loading: writing source matrices into GBCore SRAM.
  \item Result readback and correctness verification.
\end{itemize}

\paragraph{What runs on the FPGA fabric?}
\begin{itemize}[nosep]
  \item All transpose computation (diagonal BRAM fill, pipelined drain,
        write-back to SRAM).
  \item All $Q\!\cdot\!K^T$ matmul accumulation.
  \item Interrupt generation on completion.
\end{itemize}

The diagonal BRAM banking pattern is a structural property of the
FPGA design: the banking function is encoded in the hardware layout and cannot be replicated in software without simulating each bank lookup. The II\,=\,3 pipelined GBCore interface allows the transpose FSM to issue one SRAM transaction every 3 cycles with no software overhead. Moving any of this logic to host code would reintroduce exactly the off-chip bandwidth and launch-overhead costs.

\section{Methodology and Implementation}
\label{sec:methodology}
%==============================================================================

Our implementation introduces a new \texttt{Transpose} submodule in the
Lab~4 \texttt{GBModule}, resulting in four progressively optimized designs
compared in this paper. The subsections below first state how software
drives this hardware (\emph{programming model}), then describe integration
and opcodes, and finally summarize how we used HLS as a design tool
(\emph{HLS-aware optimization}).

\subsection{Programming model and software-visible constraints}

The accelerator is not invoked through a separate runtime ``kernel API'':
the host program issues 32-bit writes that \texttt{design\_top.sv} maps onto wide AXI4 beats to the Lab~4 partition ports.
\textbf{Matrix transpose} is exposed as \textbf{opcode~0} (naive SRAM
transpose) or \textbf{opcode~1} (banked-BRAM transpose); \textbf{$Q\!\cdot\!K^T$} is \textbf{opcode~2} (unfused: transpose $K$ then SRAM matmul) or \textbf{opcode~3} (fused: keep $K^T$ in local BRAM for the matmul). These behaviors live in the SystemC/C\texttt{++} \texttt{Transpose} block that Catapult synthesizes to RTL.

\begin{center}
\textbf{Lab~4 (no HW transpose)} $\to$
\textbf{Opcode~0 (naive)} $\to$
\textbf{Opcode~1 (banked BRAM)} $\to$
\textbf{Opcodes~2/3 (fused $Q\!\cdot\!K^T$)}
\end{center}

The diagonal banking function and the BRAM geometry ($32$ banks $\times$ $32$ rows) are fixed when the bitstream is built. At \textbf{run time}, software sets opcode, matrix shapes $(M,N,D)$ within the supported bounds, and GBCore base addresses through configuration writes.

Tile size in transpose BRAM is capped at $32\!\times\!32$; the GBCore path still accepts only one 128-bit element per pipelined transaction at II\,=\,3 (Section~\ref{sec:problem}). As in Lab~4, there is no off-chip DRAM. After load, compute and our transpose/matmul kernels operate on on-chip SRAM/BRAM only.

\subsection{Adding the Transpose Module}

We insert a \texttt{Transpose} submodule into \texttt{the GBModule}. The integration requires three changes to the Lab~4 design:

\begin{enumerate}[nosep]
  \item \textbf{New streaming channels:} Two new \texttt{Connections::Combinational} channels: \texttt{transpose\_large\_req} (\texttt{DataReq}) and \texttt{transpose\_large\_rsp} (\texttt{DataRsp<1>}). They connect \texttt{Transpose} to \texttt{GBCore}. GBCore's \texttt{PollNMPPort} is extended to poll this third client, serialized with NMP and GBControl using the same structure.
  \item \textbf{New AXI region (0x6):} The \texttt{GBModule} routing thread forwards address-region \texttt{0x6} to Transpose for configuration writes and \texttt{0x0}/\texttt{0x3} start triggers.
  \item \textbf{On-chip BRAM inside Transpose:} A 1024-entry flat array \texttt{bram\_flat[]} (each entry \texttt{NVUINTW(128)}) provides local scratch storage for all four opcodes. The array maps to BRAM after HLS synthesis.
\end{enumerate}

\subsection{Opcode 0: Naive Transpose (Transpose Baseline)}

The baseline traverses the $N\!\times\!D$ source matrix in column-major order.
For each element $A[r][c]$:
\begin{enumerate}[nosep]
  \item \textsc{read}: fetch $A[r][c]$ from source SRAM.
  \item \textsc{wait\_rsp}: capture the response.
  \item \textsc{write}: store the value at $A^T[c][r]$ in destination SRAM.
  \item \textsc{next}: advance counters.
\end{enumerate}
This requires \textbf{4 FSM states per element}, each costing II\,=\,3 cycles,
for a total of $12\,N\!D$ cycles.

\subsection{Opcode 1: Diagonal-Banked-BRAM Transpose (Optimized Transpose)}

We introduce 32 local BRAM banks (depth 32 each, 1024 entries total) with a
\emph{diagonal banking} scheme: element $A[r][c]$ maps to bank
$(r\!+\!c)\bmod 32$, flat address $\text{bank}\times 32 + r$. This guarantees
that any row or column accesses distinct banks, enabling conflict-free
single-cycle reads.



The optimized transpose runs in two pipelined phases:
\begin{enumerate}[nosep]
    \item \textsc{Fill phase}: (\textsc{fill\_read} $\to$ \textsc{fill\_store}):
    Read each element from SRAM into the corresponding BRAM location. Each element
    costs 2~states.
    
    \item \textsc{Drain phase}: (\textsc{drain\_first} $\to$ \textsc{drain\_pipe}):
    A single setup state pre-reads the first BRAM element; then each subsequent
    \textsc{drain\_pipe} state \emph{simultaneously} pushes the current element's
    SRAM write while speculatively reading the next element from BRAM (independent
    resources, no data dependency). Each element costs 1~state after setup.
\end{enumerate}

Overall: $2\,N\!D + 1 + N\!D = 3\,N\!D + 1$ states $\approx$ \textbf{3 states per element}. A $4/3 \approx 1.33\times$ theoretical speedup over the naive path.

\begin{figure}
  \includegraphics[width=\linewidth]{method_12.png}
  \caption{Efficient matrix transpose optimization: Opcode 0 (left) and Opcode 1 (right)}
\end{figure}

\subsection{Opcode 2: Unfused $Q\!\cdot\!K^T$}

This opcode computes $\text{Result}[i][j] = \sum_k Q[i][k] \cdot K[j][k]$ in
two sequential phases:
\begin{enumerate}[nosep]
    \item {Phase 0 -- Naive transpose:} $K(N\!\times\!D) \to K^T(D\!\times\!N)$ is written to a temporary SRAM region (memory index~3), reusing the opcode-0
    state machine.
    
    \item {Phase 1 -- SRAM-based matmul:} For each output element
    $(i,j)$, the FSM iterates over $k = 0 \ldots D\!-\!1$ and does the matmul operation.
\end{enumerate}

Each inner iteration requires \textbf{4 SRAM-bound states} (two reads: one for
$Q[i][k]$, one for $K^T[k][j]$). After $D$ iterations, one \textsc{mm\_write}
state stores the accumulated dot product. Per-element cost:
$4D + 1$ states. Total matmul cost: $M \cdot N \cdot (4D + 1)$ states, plus
the $4ND$ states for the transpose.


\subsection{Opcode 3: Fused $Q\!\cdot\!K^T$ (Transpose + Matmul)}

The key optimization: $K$ is loaded into local BRAM (fill phase only, no
write-back), and the matmul reads $K^T$ values directly from BRAM.

\begin{enumerate}[nosep]
    \item{Phase 0 -- Fill $K$ into BRAM} Identical to opcode-1's fill phase:
    $2\,N\!D$ states.

    \item{Phase 1 -- BRAM-accelerated matmul} For each row $i$ of $Q$, for
    each inner dimension $k$:
    \begin{enumerate}[nosep]
      \item \textsc{mm\_read\_q}: Read $Q[i][k]$ from SRAM (1 state).
      \item \textsc{mm\_wait\_q}: Capture response (1 state).
      \item \textsc{mm\_mac} $\times N$: For each $j$, read $K[j][k]$ from BRAM
            and accumulate $\text{accum}[j] \mathrel{+}= q \cdot k_{\text{val}}$
            (1 state each, BRAM-only).
    \end{enumerate}
\end{enumerate}

After all $D$ values of $k$, $N$ \textsc{mm\_write} states flush the
accumulators to SRAM. Per-row cost: $D(2 + N) + N$ states. Total:
$M \cdot [D(2+N) + N] + 2ND$ states.

The fused path eliminates:
\begin{itemize}[nosep]
  \item The full $K^T$ write-back to SRAM ($2ND$ states saved vs.\ unfused
        transpose).
  \item All $M\!\cdot\!N\!\cdot\!D$ SRAM reads of $K^T$ during matmul
        (replaced by single-cycle BRAM reads).
\end{itemize}
The dominant-term speedup ratio approaches $4N/(2+N)$ for large $N$:
$\sim$2$\times$ at $N\!=\!2$, $\sim$3.2$\times$ at $N\!=\!8$,
$\sim$3.6$\times$ at $N\!=\!16$.

\begin{figure}
  \includegraphics[width=\linewidth]{method23.png}
  \caption{Fused $QK^T$: Opcode 2 (left) and Opcode 3 (right)}
\end{figure}

\subsection{HLS-aware design and optimization}

The \texttt{Transpose} main FSM loop uses \texttt{\#pragma hls\_pipeline\_init\_interval 3} so that SRAM traffic through \texttt{GBCore} matches the same \textbf{II\,=\,3} contract as the rest of the global buffer; inner index loops use \texttt{\#pragma hls\_unroll yes} to flatten small counters and keep schedule predictable. To avoid Catapult splitting the scratchpad into sixteen 8-bit memories (which blew the BRAM budget in early runs), each vector is stored as a single \texttt{NVUINTW(128)} word with explicit \texttt{PackWord}/\texttt{UnpackWord} helpers. Those are memory-style
constraints comparable to \texttt{array\_partition} choices in other
HLS flows.

Trade-offs: diagonal $32$-bank BRAM buys conflict-free read patterns at the cost of fixed tile shape and extra decode logic. The fused version adds FSM complexity but removes full SRAM write-back and $K^T$ re-read traffic.

\subsection{Performance Metric}

Performance is measured in \textbf{elapsed clock cycles}, captured by a
dedicated hardware performance counter in \texttt{design\_top.sv}. \textbf{Raw} counts include a constant startup overhead.
\textbf{Adjusted} counts subtract the $1\!\times\!1$ (or
$1\!\times\!1\!\times\!1$) baseline measurement to isolate compute latency. Speedup is reported as $\text{cycles}_{\text{baseline}} / \text{cycles}_{\text{optimized}}$.

checks all output elements. All tests pass for all opcodes.

\subsection{Analysis}

\paragraph{Lab~4 baseline vs.\ hardware transpose.}
In the Lab~4 system, there is no hardware transpose; computing $K^T$ requires
transposing the matrix in host software before loading it into SRAM, or
equivalently loading it into SRAM in transposed order. This incurs a full
additional off-chip DMA transfer (read $K$ from DRAM, write $K^T$ to DRAM,
reload into SRAM), whose latency far exceeds the on-chip SRAM cost measured
here. Even opcode~0 (naive, $12\,ND$ cycles) is a strict improvement over the
Lab~4 baseline because the transpose is performed entirely on-chip with no
additional off-chip traffic.

\paragraph{Why the measured transpose speedup is less than theoretical.}
The GBCore interface serialises all SRAM accesses to one element per cycle
(II\,=\,3). The optimized transpose reduces FSM states per element from 4 to
$\sim$3, yielding a measured 1.27$\times$ speedup vs.\ the theoretical
1.33$\times$. The remaining gap is due to the one-time drain setup state and
per-phase FSM transitions. A wider SRAM port would increase the gap further,
but would require redesigning the \texttt{GBCore} arbitration logic.

\paragraph{Fusion benefit.}
The dominant cost in $Q\!\cdot\!K^T$ is the $O(MND)$ inner-loop SRAM accesses.
By keeping $K^T$ in local BRAM, the fused path replaces each 6-cycle SRAM read
(2 states $\times$ 3 cycles) with a single 3-cycle BRAM read (1 state $\times$
3 cycles). Combined with eliminating the $K^T$ write-back, the measured
3.18$\times$ speedup at $16\!\times\!16\!\times\!16$ closely tracks the
theoretical 3.56$\times$ bound, confirming the analysis.

\paragraph{Scalability.}
The 32-bank, depth-32 BRAM supports matrices up to $32\!\times\!32$ (1024
elements). For larger matrices, tiling would be required. At
$32\!\times\!32\!\times\!32$ the theoretical speedup ratio
$4N/(2\!+\!N) \approx 3.76\times$, but BRAM capacity would need to scale
with $N$ and $D$ simultaneously. Multi-head attention (e.g., BERT-base has
$A=12$ heads) could be handled by sequentially processing one head at a time,
since the per-head dimension $H/A = 64 > 32$ already exceeds the current BRAM
limit and tiling is unavoidable.

\section{Challenges and Debugging}
%==============================================================================

\paragraph{HLS resource allocation.}
Catapult initially decomposed the BRAM array into 16 separate 8-bit sub-memories,
exceeding the resource budget. We resolved this by storing BRAM entries as flat
\texttt{NVUINTW(128)} words with explicit pack/unpack functions.

\paragraph{HLS scheduling failure.}
A chained data dependency in the drain state caused scheduling failure. We split
the drain logic into a setup state (\textsc{drain\_first}) and a pipelined
state (\textsc{drain\_pipe}) to break the critical path.

\paragraph{AXI read timing (\texttt{0xDEADBEEF}).}
Early RTL simulations showed consistent data corruption
(\texttt{0x37AB6F}) because the OCL bridge returns \texttt{0xDEADBEEF} for
premature reads. We traced \texttt{0xDEADBEEF} $\gg$ 10 = \texttt{0x37AB6F}
and implemented robust polling loops in both the SystemVerilog and C testbenches.

\paragraph{Flawed performance counter.}
The original \texttt{interrupt\_cycles} counter counted cycles only while the
interrupt signal was \emph{high}---a fixed $\sim$10-cycle pulse---masking all
performance differences. We replaced it with a counter that arms on an OCL
write and stops on the interrupt rising edge.

\paragraph{No initial speedup.}
The first banked-BRAM implementation had 6 states per element (worse than
naive's 4) due to excessive SRAM handshaking. We redesigned the FSM to pipeline
fill and drain phases, achieving the current 3-state-per-element design.

\section{Conclusion}
%==============================================================================

We demonstrated a complete hardware development flow for an efficient matrix
transpose unit: from SystemC design through Catapult HLS to RTL simulation on
the AWS F2 platform. Starting from the Lab~4 system baseline---which has no
hardware transpose and requires an off-chip round-trip for any matrix
transposition---we introduce a \texttt{Transpose} module into the
\texttt{GBModule} and evaluate four design points:

\begin{itemize}[nosep]
  \item \textbf{Lab~4 (system baseline):} No hardware transpose; any $K^T$
        requires off-chip software transpose and data reload.
  \item \textbf{Opcode~0 (transpose baseline):} Naive 4-state/element
        SRAM-only transpose, $12\,ND$ cycles; first fully on-chip option.
  \item \textbf{Opcode~1 (optimized transpose):} Banked-BRAM diagonal
        scheme, 3 states/element; achieves 1.27$\times$ over opcode~0
        (vs.\ theoretical 1.33$\times$).
  \item \textbf{Opcode~3 (fused $Q\!\cdot\!K^T$):} Eliminates $K^T$
        write-back and SRAM re-reads; achieves up to \textbf{3.18$\times$}
        over the unfused opcode~2 (vs.\ theoretical 3.56$\times$ for
        $N\!=\!16$).
\end{itemize}

\paragraph{What the design does well.}
The diagonal banking scheme guarantees conflict-free column access at
design time, eliminating runtime bank-conflict overhead entirely. The
pipelined drain phase overlaps BRAM reads with SRAM writes using independent
resources, recovering one FSM state per element with no structural hazards.
The fused opcode~3 makes the speedup scale with $N$, delivering
${\sim}3\times$ gains at sizes directly relevant to Transformer attention heads.

\paragraph{Where it falls short.}
The SRAM serialisation bottleneck (II\,=\,3, one element per cycle) limits the
transpose speedup to 1.27$\times$, leaving substantial headroom compared to
designs with wider memory ports. The BRAM capacity caps supported matrix size
at $32\!\times\!32$, well below the per-head dimension of even small models
(BERT-base per-head $D = 64$). The matmul accumulator operates on 8-bit
integers without overflow protection; larger dot products would require wider
accumulators or quantisation-aware design.

\paragraph{Assumptions that may limit generality.}
The speedups assume the SRAM interface remains the dominant bottleneck. If the
system were redesigned with a wider GBCore port (e.g., 4 elements per cycle),
the fusion benefit would diminish relative to the SRAM bandwidth now available
for $K^T$ reads. The diagonal banking scheme requires the number of banks to
equal the tile dimension; irregular or non-square tiles would need a different
banking strategy. Finally, all measurements are from Vivado XSIM RTL
simulation; post-place-and-route timing and actual FPGA execution may reveal
additional bottlenecks not visible in cycle-accurate simulation.

\paragraph{Future directions.}
\begin{enumerate}[nosep]
  \item \textbf{FPGA deployment:} Program the bitstream on AWS F2 and
        measure real silicon cycle counts for all four opcodes on actual
        hardware.
  \item \textbf{Tiled transpose:} Support matrices larger than $32\!\times\!32$
        by tiling the BRAM fill/drain across multiple passes.
  \item \textbf{Full attention integration:} Extend fusion to cover
        $\text{softmax}(QK^T/\sqrt{d_k}) \cdot V$, pipelining the entire
        attention head within the global buffer.
  \item \textbf{Multi-port BRAM:} Exploit dual-port BRAM to overlap fill and
        drain, potentially doubling transpose throughput.
\end{enumerate}
